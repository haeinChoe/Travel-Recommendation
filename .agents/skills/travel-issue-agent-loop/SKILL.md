# Issue-to-PR agent loop

Run a complete, bounded implementation and review loop for an explicitly selected repository Issue. The trigger is a clear instruction such as “Implement Issue #123; PR is authorized.” Routine work inside that scope should proceed without asking the user for intermediate approval.

The Codex session that receives the user's request is the **entry coordinator**, launched with the user-level `entry-readonly` permission profile, and is read-only for repository contents. The profile extends `:read-only`; command network policy is defined by the selected user-level Codex permission profile and configuration. Its configuration includes a Herdr Unix socket rule, but CLI and MCP access must be checked independently. The coordinator inspects scope and state, plans the work, performs explicitly authorized Herdr orchestration, relays user or reviewer revision requests to the existing implementation agent, and verifies returned diffs and evidence read-only. It must not edit, test, fix, stage, commit, push, or create/update a PR in the repository. A separate **implementation agent** owns all repository mutations in its assigned worktree, subject to the Issue's and user's authorization gates. **Review agents** are read-only. Do not describe these profiles as stronger filesystem isolation than they provide.

Issue/PR work requires both this repository's `travel-issue-agent-loop` skill and the global `herdr` skill. Resolve the global skill through the current session catalog; do not assume or hardcode a global filesystem location. Follow both skills before any Herdr action. If an applicable skill is missing from the catalog, search the available skill roots as instructed by the session; stop only if a required skill cannot be found or read.

## Before implementation

1. Verify `HERDR_ENV=1`. If this is not a Herdr-managed session, do not control Herdr; report the limitation.
2. Read the repository `AGENTS.md`, `docs/agent-workflow.md`, and the selected Issue. Treat the Issue as the source for purpose, scope, non-goals, acceptance criteria, validation, and data permissions.
3. Before an actual-data run, complete the data-root preflight above. Inspect the reproduction variables in the actual user shell before relying on process environments; verify expected role structure without emitting values or paths. If the actual shell is unavailable, do not infer absence or read data. If variables are confirmed unset, bounded candidate discovery is allowed only as described above, followed by provenance, terms, authorization, and role-mapping checks before any data read.
4. Before editing, inspect Herdr server, workspace, and agent state. Prefer the registered Herdr MCP bridge's read-only inspection tools when they are available in the current session; follow [references/agent-loop.md](references/agent-loop.md) for the CLI fallback. When the equivalent MCP inspection succeeds, do not invoke the CLI as a second verification path. A configured socket rule does not guarantee direct CLI access; validate CLI only when the workflow actually requires the CLI fallback. If a direct Herdr CLI call returns `EPERM` or `Operation not permitted`, do not retry that denied command through escalation. First classify whether the call violated the execution-boundary rules below or whether the required Herdr capability itself is unavailable. A redundant or wrong-boundary CLI attempt is an orchestration defect, not by itself an Issue-level blocker; continue through the already-authorized MCP path when it provides the required state. Stop only when the required Herdr operation cannot be completed through an authorized route. Then check the clean/dirty state, current branch, existing Issue worktrees, and open PRs. Reuse or resume the same Issue's active work rather than creating duplicates. Never overwrite another worktree's changes.
5. Do not start implementation if required scope, acceptance criteria, or data access permission is missing or contradictory. Use repository evidence to resolve routine details; do not invent data meanings, contracts, or architecture decisions.

## Herdr execution boundary

Do not run Herdr CLI commands from an arbitrary repository or worktree cwd.

- Use the registered Herdr MCP bridge for supported inspection operations. If that inspection succeeds, do not repeat it with the CLI.
- `herdr pane list` and `herdr pane current --current` are optional discovery, not mandatory Issue-start preflight. If `HERDR_PANE_ID` and `HERDR_WORKSPACE_ID` are already set, do not call `pane current` only to reconfirm caller identity. An optional pane-discovery `EPERM` is not by itself an Issue-level blocker.
- When a CLI fallback is actually required, keep the coordinator in its approved orchestration execution context. Pass repository targets explicitly with documented arguments such as `--cwd "$REPO_ROOT"`; this argument identifies the repository to Herdr and does not require changing the shell cwd into that repository.
- For explicitly authorized state-changing Herdr commands with no MCP mutation equivalent (for example workspace/worktree creation, required pane creation/split, and agent start/prompt), use the global Herdr skill's approval-reviewed escalated execution route on the first attempt; do not probe them first in the ordinary command sandbox.
- Do not `cd` into a repository or worktree merely to invoke Herdr.
- After Herdr creates or resolves a worktree, verify the returned absolute path is inside the writable roots allowed by the `herdr-implementation` permission profile before starting an implementation agent.
- Implementation commands execute only in the exact worktree path returned by Herdr. Never guess, synthesize, relocate, or substitute a worktree path to recover from a permission error.
- If a denied CLI call used an invalid cwd or unapproved worktree path, do not retry that same call. Correct the orchestration boundary and continue only through an authorized path. If a state-changing command was wrongly attempted in the ordinary sandbox, use only its already-defined first-attempt approved route if that route has not yet been attempted; if the approved invocation is rejected or still returns `EPERM`, report the blocker and stop.
- Never introduce a new or broader permission route, sandbox bypass, force option, or unrestricted/default profile to recover from `EPERM`; the predefined approval-reviewed first-attempt route is not an `EPERM` recovery bypass.

## Worktree and agents

Create one dedicated Issue worktree and branch from `dev`, following `docs/agent-workflow.md` (normally `agent/<issue>-<slug>`). Use Herdr and preserve the user's current focus. The entry coordinator does not edit files in that worktree. Assign a dedicated implementation agent as the writer; it owns all edits, tests, and review fixes there. Keep every writer in a separate worktree when their file scopes are independent; use one lead implementer to integrate parallel work.

The Herdr MCP bridge provides read-only inspection plus narrowly scoped, explicitly authorized teardown tools. Use the existing authorized Herdr orchestration path for general workspace/worktree creation, agent start or prompts, and pane control. Use `herdr_worktree_remove` or `herdr_workspace_close` only when the user or Issue explicitly authorizes cleanup and the guarded procedure in [references/agent-loop.md](references/agent-loop.md) is satisfied.

Use the path and naming returned by Herdr's configured worktree flow. Before starting the writer, verify the returned path is inside the `herdr-implementation` profile's writable roots. If that location is inaccessible, identify the permission boundary before starting any agent; do not silently choose, move, or synthesize a custom location.

Do not infer that a workspace belongs to an Issue from its ID, focus state, or proximity alone. Reuse it only when the Issue branch, Git worktree path/branch, and Herdr metadata establish the mapping. Prefer a pane returned by the authorized orchestration flow; do not require a global pane-list scan merely to find a shell pane.

Choose the number of agents to fit the task:

- Small, well-bounded Issue: one implementer and one reviewer.
- Medium Issue: one implementer and one reviewer; add an independent implementer only for non-overlapping work.
- Broad or high-risk Issue: a lead plus independent implementers in separate worktrees, and one or two reviewers.

Use Codex as the default implementation agent with the user-level `herdr-implementation` permission profile; start every Codex reviewer with `entry-readonly`. These named profiles must exist in the user's Codex configuration. The implementation profile extends `:workspace`; command network policy is defined by the selected user-level Codex permission profile and configuration. Its configuration includes a Herdr Unix socket rule; check CLI and MCP access independently. Its current writable root covers the entire `~/.herdr/worktrees`, so it does not enforce per-worktree writes. If either required profile is unavailable, report the exact blocker and stop; do not silently use an unrestricted/default writer or take over in the entry session. Select profiles through Codex `--config 'default_permissions="<profile>"'`; do not combine them with legacy `sandbox_mode` or `sandbox_workspace_write`. Detailed Herdr commands, model settings, and handoff prompts are in [references/agent-loop.md](references/agent-loop.md).

## Autonomous review loop

Have the implementation agent read the Issue, repository instructions, acceptance criteria, and assigned file scope before editing. It performs edits, tests, and review fixes in its assigned worktree. It may stage and commit only when the Issue or user authorization permits; it may push or create/update a PR only when explicitly authorized, and must never merge without separate authorization. The entry coordinator verifies the implementation agent's state, actual diff, and validation evidence read-only; it does not perform repository mutations.

Ask the read-only reviewer to inspect the Issue, acceptance criteria, and full diff. Relay actionable findings, and any user-requested revisions, to the existing implementation agent; have that agent make the fixes and request a fresh review. Do not apply findings in the entry session. Repeat for at most three review rounds. Do not treat an agent's “done” message as evidence: verify the diff, working tree, validation output, and review result yourself.

Do not ask the user about routine implementation choices. Continue through the authorized work. When delivery is authorized, the entry coordinator reports the pre-push summary, then delegates the permitted commit, push, and PR steps to that same implementation agent and inspects the resulting repository state and PR read-only. The implementation agent must follow all repository authorization gates, including commit permission, explicit push/PR permission, branch restrictions, and the prohibition on merging without separate authorization. Stop only for a real blocker: missing or conflicting requirements/permissions, unavailable required access, a security concern outside the authorization, or an issue that remains unresolved after three review rounds.

## Authorized cleanup

Clean an Issue workspace only when the user explicitly requests cleanup or the Issue authorizes it. Follow the separate linked-worktree removal, linked workspace-session closure, and plain-workspace closure procedures in [references/agent-loop.md](references/agent-loop.md). Confirm the Issue-to-workspace-to-worktree-to-branch mapping, merged PR or explicit abandonment, caller/focus protection, no remaining task need, and settled agents before any operation.

For `herdr_workspace_close` on a linked workspace session, verify one exact Herdr workspace/path/branch mapping against Git, ensure the target is neither caller nor focused and its agents are settled, then verify the bridge's before/after snapshots preserve every peer ID, identity, focus, and repository provenance. Herdr may omit at most one derived `open_workspace_id` association from a peer's linked-worktree row when it referred to the closed session; preserve the row's path, branch, linked flag, and all other metadata. Git worktree and full checkout status snapshots must remain unchanged. This closes only the session and preserves its checkout, including dirty, untracked, and ignored files. Use only this guarded MCP tool path; never substitute CLI, group-close, raw API, force, or blind retries. For `herdr_worktree_remove`, a linked checkout's shared Git common directory is normal and is not, by itself, a reason to refuse removal. Verify that the exact linked checkout is clean, including untracked and ignored files, and is not on a protected branch. Plain workspace closure has separate provenance and primary-checkout ownership/cascade guards; do not apply those plain-close rules to linked-session closure or linked worktree removal.

Use only the guarded MCP teardown tools. If a call is refused or ambiguous, reread Herdr inventories and Git state, then report the exact blocker and preserve unresolved state. Do not bypass the refusal through CLI, raw APIs, group-close, force options, or blind retries. Report linked-session closure complete only after Herdr readback confirms the target session is absent and its checkout path, branch, worktree listing, and full status are unchanged. Report linked-worktree removal complete only after Herdr and Git readback confirm the requested target is absent. After a successful linked-worktree removal, delete a merged local branch only with non-force `git branch -d` when no worktree still uses it; verify the local branch is absent and leave the remote branch untouched.

## Delivery

The implementation agent prepares repository changes and, when separately permitted, staging and the local commit. The entry coordinator inspects the worktree and proposed delivery state read-only, then reports the required pre-push summary: commit log (if committed), changed files, validation results, and remaining limitations. If push/PR permission is explicit, delegate the authorized push and PR creation/update to that same implementation agent; do not perform those repository mutations in the coordinator session. The implementation agent pushes only the Issue branch and creates or updates its PR. Never push directly to `dev` or `main`; never merge, deploy, or delete worktrees unless separately authorized.

Before creating or updating a PR, the coordinator reads the target repository's instructions and any applicable PR template, then gives those conventions to the implementation agent. The implementation agent follows them; the coordinator inspects the resulting PR body and state read-only.

Finish with the branch and PR links, implementation summary, reviewers and rounds, validation performed, and any unresolved blocker. Leave the Issue worktree available for follow-up unless the user requested cleanup.
