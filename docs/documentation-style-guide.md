# 사람 중심 문서 작성 가이드

이 문서는 이 저장소의 **사람이 읽는 문서**에 적용하는 기본 작성 원칙을 정의한다. 기술적 정확성, 재현성, 안전 규칙은 그대로 유지하되, 독자가 이전 에이전트 대화나 작업 로그를 읽지 않아도 현재 상태와 판단 근거를 이해할 수 있어야 한다.

## 1. 문서의 우선 독자

문서는 작업을 수행한 에이전트보다 다음 독자를 우선한다.

- 며칠 뒤 다시 문서를 읽는 프로젝트 작성자
- 해당 실험이나 이슈에 직접 참여하지 않은 개발자
- 추천 시스템 배경지식이 있지만 이 저장소의 내부 용어는 모르는 사람
- 후속 작업을 맡는 에이전트

따라서 문서는 대화 기록이나 실행 로그의 복사본이 아니라 **현재 상태를 설명하는 기준 자료**여야 한다.

## 2. 이슈 링크 없이 이해할 수 있는 서술

**이슈 번호는 근거와 작업 이력을 찾기 위한 수단이지, 설명을 대신하는 본문이 아니다.**

- 나쁜 예: "현재 #82의 full-catalog 탐색은 #95 이후 재개하며 #83에서 평가한다."
- 좋은 예: "수도권의 약 305만 개 장소를 한꺼번에 평가했지만, 대부분의 장소가 동일한 특징값을 가져 구분이 어려웠다. 따라서 장소 표현과 추천 대상 범위를 검증하기 전에는 모델 탐색을 확대하지 않는다."
- 나쁜 예: "#96에서 서비스를 위한 로그를 설계한다."
- 좋은 예: "추천 요청 시점의 여행 상황, 사용자에게 보여준 장소, 클릭·저장 반응을 기록해 운영 이후 장소별 통계를 갱신할 수 있도록 설계한다."

본문에서는 반드시 **무엇 / 이유 / 데이터나 결정 근거 / 현재 적용 상태 / 남은 판단**을 먼저 서술한다. 이슈 번호는 해당 설명을 이해하는 데 필요하지 않은 위치에 출처로 추가하거나 문서 끝의 "근거·추적"에 모은다.

특히 README, PRD, 문서 첫 단락, 상태 안내, 로드맵, 사람을 위한 목차에서는 "이슈 번호가 무엇을 하는지" 대신 **실제 수행할 작업과 사용자·모델에 미치는 효과**를 쓴다. 같은 판단을 여러 문서에 반복할 때도 이슈 번호만 복사하지 않는다.

전문 실험 문서의 역사적 이슈·PR 번호, 버전·설정 키, 데이터 계보는 삭제하지 않는다. 다만 해당 번호만 읽고 실험 결과를 추론해야 하는 문장에는 결과와 의미를 함께 적는다.

## 3. 기본 서술 언어

일반 설명, 제목, 결론, 결정 사항은 한국어를 기본으로 한다.

다음은 원문을 유지한다.

- 코드 식별자와 데이터 컬럼명: `TRAVEL_ID`, `POI_ID`
- API 필드와 외부 규격명: `contentid`, `lDongRegnCd`
- 파일명, 클래스명, 함수명, 명령어
- 공식 알고리즘명과 평가 지표: Matrix Factorization, Two-Tower, Recall@K

전문 용어가 처음 등장하면 **한국어 설명 → 영문 원어/약어** 순서로 정의한다.

예:

- 후보 집합(candidate set): 특정 추천 요청에서 추천 대상으로 고려할 수 있는 아이템 목록
- 암묵적 피드백(implicit feedback): 클릭·방문처럼 선호를 직접 점수로 표현하지 않은 행동 신호
- 협업 필터링(Collaborative Filtering, CF)

정의한 뒤에는 한국어 표현을 우선 사용한다. 정확한 식별이 필요한 경우에만 영문을 반복한다.

## 4. 문서 상단에서 먼저 답할 것

연구·실험·설계 문서는 상세 절차보다 먼저 다음 내용을 보여준다.

1. **이 문서가 답하려는 질문**
2. **현재 상태**
3. **한눈에 보는 결론**
4. **현재 결정된 것**
5. **아직 결정되지 않은 것**
6. **다음 행동**

독자가 이 부분만 읽어도 "왜 이 문서가 있고 지금 무엇을 해야 하는지"를 알 수 있어야 한다.

## 5. 사실과 판단을 분리한다

결과를 설명할 때 다음 네 범주를 섞지 않는다.

### 확인된 사실
데이터, 코드, 실행 결과 또는 공식 문서에서 직접 확인한 내용이다.

### 해석
확인된 사실로부터 프로젝트가 어떻게 이해하고 있는지 설명한다. 해석은 사실보다 강하게 말하지 않는다.

### 결정
프로젝트에서 실제로 채택한 규칙이나 방향이다. 결정 근거와 관련 Issue를 연결한다.

### 미결정 / 추가 검증 필요
현재 근거만으로 판단할 수 없는 내용이다. 전문 용어를 사용해 확정된 계약처럼 표현하지 않는다.

관측된 상관관계를 원인으로, 실행 가능한 실험을 올바른 실험으로, 미관측 값을 음성(negative)으로 자동 승격하지 않는다.

## 6. 추천 시스템 문서의 설명 순서

알고리즘 이름보다 문제 정의가 먼저 와야 한다.

```text
제품에서 해결하려는 문제
  ↓
추천 시점에 알고 있는 정보
  ↓
사용자 / 여행 / POI / 상호작용 관계
  ↓
학습에 사용할 수 있는 신호
  ↓
추천 후보를 만드는 방법
  ↓
추천 또는 순위화 문제 정의
  ↓
평가 방법
  ↓
비교할 알고리즘
```

Matrix Factorization, Two-Tower 같은 모델을 먼저 고른 뒤 데이터 의미를 끼워 맞추지 않는다.

## 6. 표와 수치 사용 원칙

표를 보여주기 전에 **이 표로 무엇을 판단하려는지** 한두 문장으로 설명한다.

핵심 수치와 진단용 상세 수치를 구분한다.

- 본문: 결론에 직접 필요한 핵심 수치
- 상세 절: 원인 진단과 비교 수치
- 부록/재현 절: 실행 식별자, 해시, 세부 설정

실행 로그 전체를 문서에 복사하지 않는다. 재현에 필요한 명령, 입력 역할, 버전, 설정, 결과 요약만 남긴다.

## 7. 새 내부 용어를 만들 때

단순한 개념에 새로운 프로젝트 전용 영어 용어를 만들지 않는다.

새 용어가 정말 필요하면 다음을 함께 적는다.

- 한 문장 정의
- 기존 용어와 무엇이 다른지
- 이 용어가 필요한 이유
- 관련 데이터나 코드에서 어디에 대응하는지

같은 개념을 여러 문서에서 다른 이름으로 부르지 않는다. 추천 시스템 공통 용어는 [추천 시스템 용어 사전](recommendation/glossary.md)을 기준으로 한다.

## 8. 연구·실험 문서 권장 구조

새 문서는 [연구·실험 문서 템플릿](recommendation/experiment-document-template.md)을 기본으로 한다.

권장 순서:

1. 질문과 상태
2. 한눈에 보는 결론
3. 결정 / 미결정 / 다음 행동
4. 필요한 용어
5. 배경과 문제 정의
6. 데이터와 가정
7. 실험 설계
8. 결과
9. 사실 / 해석 / 결정 / 한계
10. 재현 방법
11. 상세 표 또는 부록

모든 절이 필요하지는 않다. 짧은 문서는 필요한 항목만 사용한다.

## 9. Issue와 PR 작성 원칙

Issue는 "무엇을 할 것인가"보다 먼저 **왜 필요한가와 어떤 질문에 답해야 하는가**를 보여준다.

PR은 변경 파일 목록보다 먼저 다음을 보여준다.

- 왜 변경했는가
- 결과가 무엇인가
- 기술적 의미가 바뀌었는가
- 사람이 특히 검토해야 할 부분은 무엇인가

PR에 상세 수치가 많다면 핵심 결론을 먼저 적고 상세 결과를 뒤에 둔다.

## 10. 문서 변경 검토 체크리스트

문서를 작성하거나 크게 개편한 뒤 확인한다.

- [ ] 이전 대화를 몰라도 목적을 이해할 수 있는가?
- [ ] 상단에서 현재 상태와 결론을 찾을 수 있는가?
- [ ] 처음 등장하는 전문 용어가 설명되어 있는가?
- [ ] 사실, 해석, 결정, 미결정이 구분되어 있는가?
- [ ] 표와 수치가 무엇을 판단하기 위한 것인지 설명되어 있는가?
- [ ] 재현 정보가 핵심 결론보다 앞서 독자를 압도하지 않는가?
- [ ] 기존 기술적 의미나 실험 결과를 문체 수정 과정에서 바꾸지 않았는가?
- [ ] 다른 문서와 같은 용어를 같은 뜻으로 사용하고 있는가?

문서 품질을 단순한 영문 단어 개수나 문장 길이로 자동 판정하지 않는다. 기술적 명칭을 억지로 번역하는 것보다 **맥락을 먼저 설명하는 것**이 중요하다.
