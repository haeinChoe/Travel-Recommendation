# 장소를 구별하기 위한 POI 특징 계약 — 첫 검증

> **현재 단계: 설계 초안과 검증 계획까지 작성됨. 실제 학습 데이터 기반 집계·표현력 비교는 수행하지 않았으며, 이 문서만으로 새 특징의 효과가 확인된 것은 아니다.**

## 우리가 해결하려는 문제

여행자의 특징, 이번 여행의 상황, 여행 장소의 특징을 사용해 **여행자와 장소의 적합도**를 학습하고 장소를 추천한다.

기존 수도권 실험에서는 약 305만 개 장소 가운데 대부분이 과거 인기도 0·과거 방문 유형 없음으로 표현됐다. **서로 다른 장소가 같은 특징값을 갖는 상태에서는 모델이 장소 간 차이를 배울 근거가 부족하다.** 먼저 장소마다 어떤 구별 정보가 있는지, 그 정보를 실제 추천 시점에도 제공할 수 있는지 확인한다.

이 작업의 질문은 아래 네 가지다.

1. 추천 대상으로 검토하는 장소 각각을 **무엇인지** 설명할 수 있는가?
2. 과거 방문 기록으로 **어떤 여행 문맥에서 선택됐는지** 장소별로 요약할 수 있는가?
3. 그 값이 **평가 데이터가 섞이지 않은 과거 정보**이고 실제 서비스에서도 재현 가능한가?
4. 특징을 늘렸을 때 **동일한 후보 집합 안에서** 장소를 실제로 더 잘 구별하는가?

모델의 종류와 후보 검색 구조는 이 질문 이후에 정한다.

## 핵심 구분: 장소 정보, 방문자 정보, 방문 이후 평가

| 구분 | 사례 | 의미와 주의 |
| --- | --- | --- |
| **장소의 정적 정보** | 시도·시군구, 장소 분류 코드 | 특정 방문자가 없어도 존재하는 장소 속성. AI Hub 분류 코드와 TourAPI 분류 코드를 동일한 분류체계라고 가정하지 않는다. |
| **과거 방문 관측의 통계** | 고유 여행 방문 수, 여행 시작 월별 방문 비율, 동반 형태별 방문 비율 | 장소가 **어떤 문맥에서 관측됐는지** 설명한다. 방문자가 그 장소를 선호했다거나 서비스에서 장소를 노출했다는 증거는 아니다. |
| **과거 방문 이후 평가 통계** | 만족도·추천의향 평균, 평가 응답 건수 | 방문 후 응답에 선택 편향이 있으므로 선택적 후보로만 둔다. 현재 요청 여행자의 방문 후 응답을 입력에 포함하지 않는다. |
| **요청과 장소의 궁합** | 현재 여행자의 동반 형태가 해당 장소의 과거 방문자 분포에서 차지하는 비율 | 현재 요청값을 과거 장소별 통계에 대응시킨 **설명적 궁합 값**. 이를 실제 선호 확률이라고 해석하지 않는다. |

**중요:** 원천 `TN_VISIT_AREA_INFO.VISIT_AREA_TYPE_CD`는 **방문 이벤트에 붙은 유형**이다. POI 자체의 항상 동일한 정적 분류가 아니다. 현재 `train_observed_visit_type_codes` 역시 과거 학습 방문 기록에서 재계산하는 값이다. 정적 장소 분류를 대체하지 않는다.

## 특징 후보와 서비스 재현 가능성

여기서 서비스 재현 가능성이란 **AI Hub에 그 필드가 있다는 뜻이 아니라**, TourAPI 기반 실제 서비스의 후보 장소에 **같은 의미의 값**을 제공할 방법이 있다는 뜻이다.

| 단계 | 후보 특징 | 원천 / 계산 | 서비스에서 재현하는 방법 | 채택 상태 |
| --- | --- | --- | --- | --- |
| A. 정적 정보 | 표준 시도·시군구, 위치 해석 상태 | AI Hub POI Master의 정적 코드·주소와 공식 행정구역 코드 대조 | TourAPI의 별도 위치 정보로 검증 필요; 동일한 필드/범위를 보증하지 않음 | 우선 감사 |
| A. 정적 정보 | POI Master의 장소 대·중·소분류 및 값 존재 여부 | `ASORT_LCLASDC`, `ASORT_MLSFCDC`, `ASORT_SDASDC` | TourAPI 카탈로그 분류와 의미가 다르므로 교차 매핑 전에는 서비스 호환 확정 불가 | 우선 감사 |
| B. 관측량 | 고유 여행-장소 방문 수, 고유 여행자 수, 지원 건수, `log1p` 방문 수 | 선택한 학습 코호트의 **내부 학습** 방문 기록만 집계 | 서비스의 확인된 방문 기록이 있을 때만 동일한 의미로 재현. 클릭/저장은 방문과 다르게 표시 | 조건부 후보 |
| C. 여행 시기 | 장소별 **여행 시작 월**에 따른 방문자 분포 | `trip_context.start_month`와 내부 학습 여행-장소 기록 | 추천 요청의 여행 시점을 기록하고, 긍정 행동 로그가 누적된 뒤 해당 행동의 월별 분포를 계산 | 조건부 후보 |
| D. 동반 형태 | 장소별 동반 유형 분포 | `companion_status`, 고유 내부 학습 여행-장소 기록 | 추천 요청에 입력된 동반 유형과 해당 장소에 연결된 선택적 행동 로그 | 조건부 후보 |
| D. 여행 동기 | 여행 동기 **순위별** 관측 분포 | `travel_motive_1..3`, 고유 내부 학습 여행-장소 기록 | 서비스가 같은 의미의 여행 동기를 요청 시 수집해야 함 | 조건부 후보 |
| D. 여행 스타일 | 설문 8문항 각각의 코드 분포 | `travel_style_1..8`, 고유 내부 학습 여행-장소 기록 | 서비스에서 같은 문항·코드 의미로 수집하거나 별도 변환을 검증해야 함 | 조건부 후보 |
| E. 과거 평가 | 만족도/재방문의향/추천의향 분포와 각 응답 수 | 실제 **내부 학습 방문 이벤트**에서 평가가 유효한 행만 집계 | 사용자에게 방문 후 선택적 피드백을 별도로 받아야 함 | 기본 입력에서 제외; 선택적 실험 |
| 보류 | 원시 GPS, 방문 체류시간, 임베딩, 이미지·자유 텍스트 | 현재 온라인 수집·동의·동일 의미 재현 경로가 확인되지 않음 | 별도 제품·데이터 계약 필요 | v1 기본 범위 밖 |

서비스에서 **노출 → 클릭 → 저장**을 수집할 수 있어도 `click_count`를 `visit_count`로 바꿔 계산하지 않는다. 두 신호는 다른 의미이므로 별도 컬럼과 버전을 사용한다.

### 표현의 두 층

기본값은 `정적 정보(A)`다. 방문 관측이 0인 신규 장소도 시도·시군구, 확인된 장소 분류와 결측 상태만으로 표현할 수 있어야 한다.

방문 관측이 충분한 장소에는 `과거 행동(B~D)`을 추가할 수 있다. 응답이 있는 장소에는 선택적으로 `과거 평가(E)`를 비교한다. 단 **장소 인기도가 크다는 사실만으로 추천 적합도가 높다고 가정하지 않는다.**

## 학습 자료 경계와 집계 규칙

### 데이터 사용 범위

- **개발용 학습 데이터(TL):** 여행자 단위로 내부 학습과 내부 검증으로 분할한다.
- **내부 학습 여행만:** 장소의 관측량, 시기·동반자·동기·스타일 분포, 과거 평가 통계를 만든다.
- **내부 검증 여행:** 그 여행의 요청 문맥만 입력으로 사용한다. 그 여행의 방문 기록은 **특징 생성에 사용하지 않고** 별도 평가 신호로만 보유한다.
- **정적 장소 마스터(OTHER):** 실제로 확인된 정적 장소 정보에 한해 사용한다. 방문 결과를 이용해 결측 정적 분류를 추정해 채우지 않는다.
- **공식 검증 데이터(VL):** 특징 선택·코호트 결정·지표 개선에 사용하지 않고 최종 설정 확정 전에는 읽지 않는다.

현행 분할 키는 권역과 여행자 식별자의 조합 `(region, TRAVELER_ID)`이고, 추천의 한 묶음은 여행/요청이다. 원래 식별자는 조인·중복 제거·분할 검증용 키일 뿐 모델 특징에 넣지 않는다.

### 방문 기록 단위

**한 여행이 같은 POI를 여러 차례 방문했더라도**, 여행-장소 방문 수에는 최대 1회만 더한다. `trip_item_interaction`의 여행-장소 관측 단위를 우선 사용하며, 반복 방문 이벤트 수는 별도 진단값으로만 보존한다.

- `observed_trip_count(i)` = 해당 장소를 방문한 **서로 다른 내부 학습 여행의 개수**
- `observed_traveler_count(i)` = 해당 장소를 방문한 **서로 다른 내부 학습 여행자 수**
- `visitor_profile_support(i, field)` = 해당 장소 방문 여행 중, **그 필드가 유효하게 관측된 여행 수**
- `visitor_profile_share(i, field=value)` = 그 유효한 여행 중 지정 값의 비율

분모가 0이면 **0%가 아니라 결측/해당 통계 없음**으로 기록한다. 함께 지원 건수를 남긴다. 비율을 만들 때는 결측을 값 0으로 취급하거나 분모에 포함하지 않는다.

동일 여행자의 반복 여행이 들어오면 `observed_trip_count`와 `observed_traveler_count`는 달라질 수 있다. 둘을 같은 통계로 간주하지 않는다.

### 문맥의 의미를 임의로 바꾸지 않기

- `start_month`는 **여행 시작 월**이다. 방문 개별 일자의 월이라고 부르지 않는다.
- `travel_motive_1/2/3`은 **서로 다른 우선순위**다. 별도 승인 없이 단순 합산해 같은 동기로 취급하지 않는다.
- `travel_style_1..8`은 8개 문항의 코드 응답이다. 공식 문항 해석이 확인되지 않은 상태에서 ‘자연 선호’, ‘문화 선호’ 같은 새 의미로 묶지 않는다.
- `companion_status`와 `companion_count`는 서로 다른 정보다.
- `source_category_l1..3`는 POI Master의 정적 코드다. TourAPI 분류명과 같다고 가정하지 않는다.

### 코호트·장소 식별 경계

기존 탐색은 관광 방문 유형(`tourism_core`)의 일부만 양성으로 삼았다. 그러나 **실제로 방문했지만 관광 코호트에서 제외된 식당·카페·숙박 등**을 미관측으로 바꾸거나 비교용 음성으로 처리하면 방문 사실과 학습 라벨이 충돌할 수 있다.

따라서 v1의 핵심 비교는 **어떤 코호트로 집계했는지 명시**한다. 관광 방문 코호트와 전체 유효 방문 코호트를 조용히 섞지 않는다. 새 제품 추천 범위가 정해지지 않은 단계에서는 양성 코호트를 임의 확장/축소하지 않는다.

또한 `TN_VISIT_AREA_INFO.POI_ID`와 `TN_POI_MASTER.POI_ID`가 언제나 검증된 외래키 관계라고 가정하지 않는다. 정확히 결합된 장소와 결합할 수 없는 방문 사례의 비율은 **별도 집계로 보고**하고, 누락된 장소를 그럴듯한 문자열 매칭으로 조용히 복구하지 않는다.

## 궁합 특징을 만들 때의 조건

예를 들어 여행자의 동반 유형이 '가족'이고 POI에 내부 학습 방문 중 동반 유형이 '가족'이었던 여행이 10개/전체 유효 20개라면, `companion_profile_share=0.5`로 입력하는 방식은 검토할 수 있다.

하지만 이 값은 **'이 장소를 방문한 여행 중 가족 여행의 비율'**이지 **'가족 여행자가 이 장소를 방문할 확률'**이 아니다. 모든 가족 여행자가 어떤 후보를 보았는지 기록되지 않았으므로 후자라고 말할 수 없다.

실험 시에는 사용자의 문맥 컬럼을 그대로 넣는 방식과 궁합 값을 추가하는 방식을 **같은 후보·동일 분할** 아래 비교한다. 방문 수가 적은 장소의 비율을 과신하지 않도록 분모와 결측 상태를 모델에 함께 전달하며, 평활화 규칙을 쓴다면 공식과 계수를 따로 기록한다.

## 실제 데이터에서 먼저 확인할 항목

**데이터 접근 권한을 가진 전담 데이터 분석 작업만** 실제 원본을 확인한다. 이번 문서 작성에서는 어떤 실제 TL·VL 원본도 열거나 새 결과를 계산하지 않았다.

### 장소 정적 정보의 가용성

- 같은 후보 집합을 고정했을 때 위치 해석 상태와 시도/시군구 코드의 유효 비율
- 대·중·소분류의 각각 유효 비율, 정적 분류와 장소 유형의 교집합 유효 비율
- 원천 POI Master와 방문 기록이 연결된 비율; 연결 실패 이유 집계
- 정확한 주소·좌표·식별자 없이 **비식별 집계만** 출력

### 방문자 프로필을 만들 수 있는 정도

- 동일 후보 집합 안의 장소별 고유 **내부 학습 여행** 관측 수: **0, 1, 2~4, 5~9, 10 이상**
- 고유 여행자 지원 수 분포
- 시작 월 / 동반 유형 / 동기 순위 / 스타일 문항별 **유효 응답 지원 수**, 전체 후보 중 분포 계산 가능한 장소의 비율
- 코호트 및 정적 장소 결합 실패를 별도 분모로 보고

### 얼마나 더 잘 구별되는가?

**같은 후보 집합, 같은 내부 학습/검증 분할, 같은 결측 규칙**으로 다음을 누적 비교한다.

| 비교 단계 | 추가하는 특징 | 질문 |
| --- | --- | --- |
| 기준 | 기존 행정 위치 + 인기도 + 과거 방문 유형 | 이전 특징 조합의 구별력을 다시 재현할 수 있는가? |
| 정적 정보 | 장소 유형의 정적 근거(있을 때) + 대·중·소분류와 결측 상태 | 적어도 과거 방문 없는 장소가 구별되는가? |
| 계절 | 여행 시작 월별 방문자 분포 + 유효 응답 건수 | 특정 시기에 주로 방문되는 장소를 구별하는가? |
| 동반·목적·스타일 | 각 항목의 값 분포 + 지원 건수 | 방문자 문맥의 차이를 구별할 수 있는가? |
| 선택적 평가 | 과거 평가 집계 + 응답 건수 | 명시적 피드백이 있는 장소에서만 추가 구별력이 생기는가? |

각 단계마다 **고유 장소 특징 조합 수**, **동일 조합을 공유하는 후보 수와 비율**, **가장 큰 동일 조합 그룹 크기**, **기본값 외 값을 가진 장소의 비율**, **관측 지원 구간별 결과**를 기록한다.

기존 '729개 특징 조합' 측정과 비교하려면 그 실험의 후보 약 305만 개를 **정확히 같은 범위로 재현했을 때만** 수치를 나란히 놓는다. 실제 추천 가능 장소만 새로 추린 경우에는 **별도의 분모와 실험**으로 보고하며, 두 결과의 구별력 개선을 같은 실험이라고 주장하지 않는다.

## 합성 데이터 검증 조건

실제 자료를 읽기 전에 가상의 여행·장소 데이터로 다음을 통과해야 한다.

1. **누수 방지:** 내부 검증 여행의 방문·만족도를 변경해도 내부 학습에서 만든 장소 특징이 달라지지 않는다.
2. **중복 제거:** 동일 여행에서 같은 장소를 반복 방문해도 `observed_trip_count`가 증가하지 않는다.
3. **분모 처리:** 동반 유형이 결측인 여행은 `companion_profile_share`의 분모에서 빠지고, 해당 지원 건수만 감소한다.
4. **새 장소:** 방문 관측이 0인 장소도 정적 위치·분류와 지원 건수 0을 갖는다. 빈 분포를 임의 0%로 만들지 않는다.
5. **동기와 스타일:** 순위 문항·8개 스타일 문항을 임의로 섞어 합산하지 않는다.
6. **코호트 분리:** 실제로 관측된 비핵심 방문이 자동으로 '미관측/불호'로 바뀌지 않는다.
7. **평가 불변:** 내부 검증 긍정 사례를 후보에 사후 주입하거나 장소 과거 통계에 넣지 않는다.
8. **서비스 호환성:** AI Hub 분류 코드를 TourAPI 코드로 이름만 바꿔서 동일 특징이라고 통과시키지 않는다.

## 현재 확정된 것과 남은 결정

**현재 확정한 방법:** 정적 장소 정보와 내부 학습에서 만든 과거 방문자 통계를 구분한다. 단위·분모·결측·누수·서비스 재현성을 명시한다. 새 장소는 정적 정보로 표현한다. 모델 복잡도를 높이기 전에 동일 후보 안의 장소 구별력을 검증한다.

**아직 검증하지 못한 것:** 실제 TL의 특징 가용률, 관측 지원 분포, 특징 조합 수의 개선, 어떤 특징 그룹이 추천 성능에 유용한지, 어떤 방문 유형을 최종 학습 양성으로 쓸지, TourAPI에서 AI Hub 분류와 동일 의미의 특징을 만들 수 있는지. **수치 없이 완료로 표시하지 않는다.**

**다음 작업:** 승인된 전담 데이터 분석 경로로 실제 **TL 내부 학습 데이터만** 사용해 위 집계를 계산하고 비식별 결과를 보고한다. 지원이 충분한 특징만 선정한 뒤 단순한 적합도 모델을 같은 후보·분할에서 다시 평가한다. 공식 VL은 마지막 모델 설정 확정 후에만 사용한다.
